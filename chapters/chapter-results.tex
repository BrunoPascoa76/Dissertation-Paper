\subsection{Servidor}
\label{sec:final_state_server}

Apesar da escolha mais importante ser no tipo de tecnologia (como \ac{MQTT} ou \ac{TSDB}), o desenvolvimento de uma solução real requer que escolhamos as ferramentas específicas que implementem estas tecnologias.

Para os \textit{brokers} local e remoto, escolhi optar pelo Mosquitto.
Apesar de existirem outras implementações de \ac{MQTT} como o ActiveMQ que possuem melhor \textit{performance} em escala (por utilizarem todos os recursos disponíveis), o Mosquitto continua a ter uma melhor \textit{performance} em cenários com recursos limitados~\cite{Mishra2021}.
Esta qualidade pode ser útil para o \textit{broker} remoto em cenários N:1 (como o descrito na Secção~\ref{sec:chosen_technologies}), mas torna-se particularmente útil para o \textit{broker} local quando este é executado em computadores com recursos mais limitados (como, por exemplo, \textit{Chromebooks}), onde a execução em paralelo com \textit{software} de videochamada (como o Zoom) poderá limitar severamente os recursos disponíveis.
Outra vantagem inerente ao Mosquitto que levou a esta decisão, foi o mecanismo de redirecionamento \textit{\ac{MQTT} Bridge} que permite enviar as mensagens do \textit{broker} local para o \textit{broker} remoto de forma automática sem comprometer as garantias de entrega.

Em termos de armazenamento de dados, decidi optar pelo InfluxDB por ser uma base de dados criada de raiz para lidar com séries temporais, ao contrário de bases de dados como o TimescaleDB, que foi criada como extensão ao PostgreSQL~\cite{influxdata2026}.
Esta diferença permite ao InfluxDB oferecer maior velocidade de ingestão, o que é uma qualidade útil neste caso de uso, que consiste maioritariamente de escritas constantes de pequeno tamanho~\cite{OctaByte2025}.
Adicionalmente, após a versão 3, o InfluxDB oferece agora a possibilidade de realizar \textit{queries} utilizando \ac{SQL} \textit{standard}~\cite{influxdata2026}, removendo assim a barreira de aprendizagem para programadores, uma das vantagens atribuídas ao TimescaleDB

Finalmente, durante a integração do Kafka Connect no servidor, foi registado um erro pontual na conversão entre os formatos \textit{Bytes} e \ac{JSON} (necessário para a inserção na base de dados): se um sensor produzir um valor do tipo \textit{Float} com parte decimal nula (por exemplo, \texttt{1.0}), este valor é convertido para \textit{Integer} após a conversão para formato \ac{JSON}, o que causa um erro de inserção na base de dados (que apenas aceita um \textit{Float} para aquele campo).
Apesar de reconhecer a existência de soluções conceptualmente mais robustas, como, por exemplo, a inclusão explícita do \textit{schema} na própria mensagem, a raridade deste erro dificultou a sua deteção precoce. Por esta razão, os constrangimentos temporais tornaram necessária a adoção de uma solução mais pragmática: a adição de um valor decimal infinitesimal (inferior à margem de erro do próprio sensor) em todos os valores do tipo \textit{Float}, evitando assim que sejam convertidos para \textit{Integers}.

\subsection{Aplicação}

Para além de servir como ponto principal de interação para os utilizadores monitorizados, a aplicação é também, geralmente, o único componente (para além da visualização) que necessita ser modificado para suportar uma nova fonte de dados, já que é o único componente que processa os dados de cada sensor de forma diferente.

Por estas razões, o foco principal das decisões de implementação da aplicação não foi necessariamente otimizar \textit{performance}, mas sim facilitar a utilização e modificação da aplicação, mesmo para indivíduos sem experiência em programação.

Em termos de modificação, para além de escolher o Python como linguagem de programação por ser uma linguagem fácil de aprender e compreender para principiantes~\cite{John2025}, decidi mitigar ainda mais o esforço de modificação ao isolar a lógica de interação com cada sensor em classes separadas carregadas dinamicamente durante a inicialização da aplicação.
Desta forma, para recolher dados de um novo sensor, é apenas necessário estender uma classe base (que possui dois métodos: uma para iniciar a recolha e uma para terminar a recolha) e adicionar a nova classe a uma pasta específica.

Em termos de interação, como considero importante cada utilizador monitorizado ser capaz de começar e terminar a monitorização de forma autónoma, e tendo em conta que não é exequível pressupor que todos os utilizadores tenham experiência com terminais, decidi optar por uma interface gráfica, de modo a facilitar a interação e para permitir a possível adição futura de mecanismos de alarme em caso de falha de sensores (sendo a escolha do PyQT6 como implementação específica comparativamente trivial)

Finalmente, em termos de ambiente de execução, apesar de ter inicialmente considerado a utilização do Docker para isolamento do sistema do seu ambiente, a necessidade de acesso a baixo nível aos periféricos para recolha de dados tornou a contentorização da aplicação impraticável.
Contudo, decidi optar por uma abordagem intermédia, utilizando contentores Docker apenas para o \textit{broker} local e atribuindo a responsabilidade de inicializar e interromper a execução do \textit{broker} à aplicação, removendo assim a necessidade de executar o \textit{broker} separadamente.

\subsection{Recolha de Dados}

Apesar da escolha de fontes de dados ter apenas como propósito demonstrar o sistema em funcionamento, a escolha destas fontes de dados continua a ter um impacto no sistema, quer seja devido a restrições associadas a certos modelos de \textit{wearable} ou devido à natureza possivelmente sensível de alguns dos dados recolhidos.

\subsubsection{\textit{Smartwatch}}

Em primeiro lugar, de forma a demonstrar a integração com fontes de dados externas, foi-me disponibilizado pelo orientador o \textit{smartwatch} \textit{Xiaomi Watch 2}.

Embora a intenção durante a conceção inicial do projeto tenha sido a extração do \ac{HRV} (por ser a métrica utilizadas nos artigos revistos~\cite{facial_hrv_study}) via \ac{BLE} (por ser uma interface exposta de forma nativa pelo próprio \textit{wearable}), a falta de documentação e experiências empíricas levaram à conclusão de que ambas as funcionalidades seriam inviáveis, pelo menos para este modelo, sendo que por isso optei por extrair o \ac{BPM} e comunicar com a aplicação via \ac{MQTT}.
Apesar da mudança de métricas ter sido uma escolha comparativamente trivial, a decisão de comunicar via \ac{MQTT} teve um maior impacto na arquitetura, pois não só exigiu a criação de uma aplicação executada no próprio \textit{smartwatch} mas também foi um dos fatores que solidificou a adição do \textit{broker} local à arquitetura.

Esta aplicação comunica principalmente através do \textit{broker} local, não só enviando os dados diretamente para este \textit{broker} mas também subscrevendo a um tópico de onde recebe instruções para iniciar ou terminar a recolha (sendo que a instrução de início de recolha contém também o \ac{UUID} necessário para a identificação do utilizador).

Finalmente, como o endereço IP do \textit{broker} local é diferente para cada utilizador, torna-se também necessário implementar um mecanismo de descoberta. 
Como este processo é geralmente realizado apenas uma vez, não considerei necessário implementar um mecanismo de descoberta automática, optando pela geração e introdução de um código de emparelhamento de 12 dígitos (que codifica o endereço IP e porta do \textit{broker}), codificado utilizando o padrão Crockford Base64 (uma variante do Base64 que remove caracteres visualmente similares para evitar erros de digitação).

\subsubsection{Câmara}

A câmara foi escolhida como periférico por duas razões: por ser uma fonte de dados periódica, ou seja, que produz dados a um ritmo constante (ao contrário do teclado), mas também por produzir dados que necessitam ser processados antes de serem inseridos na base de dados.

Para a recolha destes dados, decidi utilizar a biblioteca ``Mediapipe'', não só por se integrar diretamente no Python, mas também porque permitir a extração em tempo real de \textit{landmarks} faciais através de um modelo local (suportando um total de 478 pontos faciais), realizando assim de forma automática o primeiro passo no processamento: a transformação de uma imagem num conjunto de coordenadas.

Contudo, apesar de ser tecnicamente possível armazenar diretamente estes \textit{landmarks} na base de dados (ao atribuir um campo a cada ponto), os \textit{landmarks} faciais continuam a ser um dado sensível (por permitirem a reconstrução da face), exigindo por isso cuidados especiais para garantir a privacidade do utilizador.
Por esta razão, e tendo em conta que os dados dos sensores têm um propósito meramente demonstrativo, decidi adotar uma política de "privatização na fonte", calculando as métricas (orientação facial e \ac{EAR}) diretamente na aplicação e enviando apenas estes dados, mitigando assim problemas como privacidade.

\subsubsection{Teclado}

Finalmente, como ambas as fontes de dados anteriores possuem uma natureza periódica, ou seja, produzem amostras a uma frequência constante, decidi também recolher dados do teclado pela sua natureza aperiódica, já que é apenas produzindo um valor quando o utilizador pressiona uma tecla, sendo por isso a frequência de amostragem não só irregular, mas também uma das métricas para análise.

Em termos de privacidade, apesar do teclado não permitir identificar diretamente o indivíduo, ao contrário da câmara, os dados de digitação puros continuam a ser dados altamente sensíveis, pois não só permitem monitorizar conversas privadas, mas também extrair credenciais como palavras-passe.
Felizmente, como o objetivo geral é monitorizar a dinâmica de digitação em si e não o conteúdo do texto, é possível anonimizar os dados ao atribuir uma categoria a cada tecla (alfanumérico, caractere especial, \textit{whitespace} ou \textit{delete/backspace}). Considerei esta abordagem como a mais apropriada, pois evita a reconstrução do conteúdo digitado sem afetar o cálculo de métricas como velocidade de digitação ou taxa de correção.

\subsection{Visualização}

Para permitir ilustrar o sistema em funcionamento, decidi implementar um \textit{dashboard} Grafana (Figura~\ref{fig:grafana}). Este \textit{dashboard} utiliza o InfluxDB como fonte primária de dados e permite, para um dado utilizador (identificado via \ac{UUID}), não só visualizar em tempo real os últimos valores registados pelas três fontes de dados, mas possui também um gráfico para cada que demonstra a evolução histórica de cada métrica associada (sendo a métrica associada ao teclado calculada dinamicamente pelo próprio Grafana).
A escolha do Grafana como \textit{software} de visualização deve-se não só à sua facilidade de uso e compatibilidade com InfluxDB, mas também por ser compatível com ferramentas de observabilidade como o Prometheus ou Jaeger, permitindo assim a deteção mais fácil de falhas na aplicação (esta última funcionalidade, apesar de planeada, não foi implementada devido a constrangimentos temporais).

\section{Estimativa de Carga e Capacidade do Sistema}

Dado o caráter demonstrativo do protótipo e o foco do trabalho na validação concetual da arquitetura, a avaliação de desempenho centrou-se no dimensionamento preliminar da carga e da capacidade de ingestão. Esta análise permite inferir a viabilidade operacional do sistema através da caracterização da pegada de transmissão (\textit{network footprint}) e da estimativa do débito de dados previsível.

\subsection{Tamanho das Mensagens}

A estrutura da mensagem, serializada em formato \ac{JSON} (como visto na Listagem~\ref{code:example_message}), foi desenhada para ser concisa, apresentando um payload médio de 133B para o \ac{JSON} em si (valor obtido através da serialização de uma das mensagens) e cerca de 173B se incluirmos os \textit{headers} de TCP/IP.

Considerando este volume de dados inexpressivo, o fator determinante para a escalabilidade da infraestrutura é exclusivamente o número de mensagens simultâneas que o broker consegue processar por segundo, e não o tamanho individual de cada pacote. Uma vez que a estrutura é simples e não exige processamento complexo ao nível da camada de transporte, o sistema é capaz de suportar um débito elevado de eventos, sendo a capacidade de ingestão limitada primariamente pela cadência de publicação (\textit{throughput}) e não pela ocupação da largura de banda.

\section{Discussão}

Como o objetivo principal deste trabalho era servir como prova de conceito que fundamente a viabilidade do paradigma \textit{streaming} para cenários de monitorização contínua de múltiplos utilizadores durante o uso normal do computador, é necessário não só demonstrar a operabilidade prática, mas também avaliar em que medida esta prova de conceito fundamenta a viabilidade do paradigma de \textit{streaming} e das tecnologias existentes no cenário descrito.

\subsection{Agnosticismo no Servidor}
\label{sec:discussion_agnostic}

A decisão de manter o servidor agnóstico ao número de fontes de dados e as suas características, sendo conhecidos apenas pela aplicação e pelo \textit{software} de visualização, permitiu que a adição de um novo sensor se limitasse à aplicação, na qual é necessário apenas criar uma nova classe e inserir o respetivo ficheiro na pasta correspondente, e ao \textit{software} de visualização.
Esta propriedade pode ser comprovada através da análise dos próprios componentes, onde as únicas referências às três fontes de dados (teclado, câmara e \textit{smartwatch}) em código se encontram nestes componentes (e na aplicação para WearOS), apesar de cada fonte de dados possuir características e métricas diferentes.

Contudo, esta escolha tem um custo direto: como o servidor desconhece a natureza dos dados que transporta, não é possível estabelecer fluxos de processamento distintos para cada fonte de dados sem violar este princípio de agnosticidade, sendo por isso necessário realizar o processamento na aplicação ou de forma dinâmica durante a visualização.
O erro de conversão apresentado na Secção~\ref{sec:final_state_server} é, de certa forma, uma consequência indireta desta limitação, pois, como o Kafka Connect desconhece que dados estão a ser transportados, necessita inferir os seus tipos com base nas mensagens, cuja ambiguidade leva a erros pontuais na inserção.

\subsection{Reutilização de Ferramentas Estabelecidas}

Como o objetivo principal do trabalho não é demonstrar a minha capacidade de implementar um sistema de monitorização contínua de raiz, mas sim demonstrar a viabilidade do \textit{streaming} como paradigma, o que exige demonstrar que as tecnologias e protocolos de \textit{streaming} já existentes são capazes de realizar esta monitorização contínua.

Esta decisão de priorizar soluções já existentes para a resolução de problemas traduziu-se, por exemplo, na ausência de \textit{workers} de transporte construídos de raiz: optando por resolver os problemas de encaminhamento entre o \textit{broker} local e o servidor através do mecanismo \ac{MQTT} Bridge e a interação com o Kafka através do Kafka Connect.

O custo principal desta decisão foi a necessidade de implementar componentes adicionais, como o \textit{broker} remoto, que não seria necessário se um \textit{worker} consumisse os dados do \textit{broker} local e os enviasse diretamente para o Kafka, bem como a exposição às restrições associadas ao funcionamento das próprias ferramentas (por exemplo, o conector \textit{source} \ac{MQTT}, apesar de ser capaz de consumir de múltiplos tópicos \ac{MQTT} através do uso de \textit{wildcards}, apenas consegue inserir num único tópico Kafka).

\subsection{Privatização na Fonte}

A decisão de calcular as métricas referentes aos dados faciais e à atribuição de categorias às teclas premidas, evitando assim a transmissão de dados sensíveis de alto risco como \textit{landmarks} faciais ou texto digitado, bem como a opção da identificação de cada utilizador somente através de um \ac{UUID} aleatório gerado durante a primeira recolha, responde diretamente a uma das barreiras à adoção deste tipo de monitorização identificadas na literatura (Secção~\ref{sec:soa_data_sources}).
Esta abordagem tira partido da limitação de processamento referida na Secção~\ref{sec:discussion_agnostic}, que incentiva o processamento na fonte, para eliminar o maior risco de segurança neste tipo de sistemas (a recolha de dados sensíveis e o risco do acesso indevido ao mesmo) e, no caso da câmara, reduzir drasticamente o volume de dados transmitidos (reduzindo de 478 pares de valores, no caso do Mediapipe, para apenas 3 métricas).

Contudo, esta escolha tem dois impactos principais: a delegação do processamento para o cliente não só aumenta o consumo de recursos, mesmo que não de forma drástica, mas também implica que os dados estão disponíveis apenas como métricas finais, ou seja, se for necessário ajustar ou alterar as métricas a monitorizar, todos os dados históricos terão de ser descartados por ainda utilizarem as métricas antigas.

\subsection{Heterogeneidade das Fontes de Dados}

A escolha de fontes de dados com comportamentos diferentes permitiu demonstrar a capacidade do sistema para lidar com fontes de dados periódicas e aperiódicas, bem como internas e externas.

Contudo, apesar de demonstrar a integração com \textit{smartwatches} WearOS através de \ac{MQTT}, esta não garante compatibilidade do sistema com todos os dispositivos \textit{wearable off-the-shelf}, como, por exemplo, \textit{smartrings} que comunicam geralmente via \ac{BLE} ou \textit{smartwatches} com outros sistemas operativos, onde a execução de aplicações de terceiros é mais complexa ou até mesmo impossível.

\subsection{Limitações Gerais}

Para além das limitações acima descritas, este trabalho apresenta um conjunto de limitações que decorrem diretamente do seu caráter de prova de conceito e dos constrangimentos temporais associados:
\begin{itemize}
    \item O sistema foi avaliado por um único utilizador (o próprio autor) num cenário unipessoal, sendo por isso a \textit{performance} em escala baseada numa estimativa de carga e com base nas características individuais das próprias ferramentas e não em testes de carga empíricos
    \item Não foi medida de forma automática a latência entre a produção dos dados e o seu armazenamento e visualização. Consequentemente, não foi verificado o possível impacto da distância física entre cliente e servidor no tempo de propagação das mensagens
    \item A avaliação da extensibilidade do sistema foi baseada no isolamento estrutural da alteração, reduzindo ao máximo a quantidade de código e componentes a serem revistos, e não a testes reais envolvendo utilizadores com diferentes níveis de experiência em programação
    \item Embora a privatização dos dados ter reduzido drasticamente os riscos de segurança inerentes ao sistema, reconheço que deveria ter implementado melhores mecanismos de segurança e controlo de acesso, nomeadamente ao nível da autenticação e de controlo de acesso ao \textit{broker} remoto. Estas questões foram ponderadas durante o desenho do sistema, mas a sua implementação efetiva acabou por ser deliberadamente omitida face aos constrangimentos temporais da prova de conceção, constituindo uma lacuna relevante para a robustez da solução fora de um ambiente controlado
\end{itemize}
