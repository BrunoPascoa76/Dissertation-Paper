\subsection{Ingestão e Transporte de Dados}
\label{sec:final_state_server}

Devido ao impacto que cada componente relacionado à ingestão e transporte tem nos restantes, as escolhas referentes à implementação foram realizadas antes da implementação, estando descritas em detalhe na Secção~\ref{sec:chosen_technologies}.
Por isso, as escolhas tomadas durante a própria implementação foram comparativamente triviais, sendo apenas necessário escolher implementações específicas para o protocolo \ac{MQTT} e para a \ac{TSDB}.

\subsubsection{\ac{MQTT}}

Para os \textit{brokers} local e remoto, foi escolhido o Mosquitto como implementação específica do protocolo \ac{MQTT}.
Apesar de outras implementações de \ac{MQTT} - como o ActiveMQ, por exemplo - possuírem melhor \textit{performance} em escala - por utilizarem todos os recursos disponíveis - o Mosquitto continua a ter uma melhor \textit{performance} em cenários com recursos limitados~\cite{Mishra2021}.
Esta qualidade é especialmente neste cenário de tutoria, uma vez que o sistema (ou, no mínimo, a componente local) será executada num computador pessoal em paralelo com as ferramentas de tutoria e de videochamada habituais, o que incentiva a minimização do consumo de recursos computacionais.

\subsubsection{\ac{TSDB}}

Em termos de armazenamento de dados, existem duas principais opções para \ac{TSDB}: InfluxDB e TimescaleDB~\cite{influxdata2026,OctaByte2025}.

O TimescaleDB foi criado como uma extensão de PostgreSQL para o otimizar para dados temporais ao utilizar tabelas distribuídas particionadas por tempo~\cite{influxdata2026}.
A principal vantagem do TimescaleDB é que continua a ser uma base de dados relacional, sendo a melhor escolha para casos de uso híbridos que envolvam a união entre dados relacionais e temporais ou para sistemas que já utilizam PostgreSQL~\cite{OctaByte2025,influxdata2026}.

Por outro lado, o InfluxDB foi criado de raiz para armazenar dados temporais, o que lhe permite oferecer uma melhor \textit{performance} em termos de ingestão de dados e otimização do espaço de armazenamento~\cite{OctaByte2025}.
Adicionalmente, após a versão 3, o InfluxDB oferece agora a possibilidade de realizar \textit{queries} utilizando \ac{SQL} \textit{standard}~\cite{influxdata2026}, removendo assim a barreira de aprendizagem para programadores, uma das vantagens atribuídas ao TimescaleDB.

Apesar do TimescaleDB ser uma escolha possivelmente mais apropriada para cenários com dados híbridos (como, por exemplo, empresariais), o sistema proposto armazena apenas os dados de monitorização, o que levou à escolha do InfluxDB como implementação específica de \ac{TSDB}.

\subsubsection{Problemas Encontrados}

O único problema relevante encontrado durante a implementação do mecanismo de ingestão e transporte foi um erro pontual registado no Kafka Connect: durante a conversão entre tipo de dados antes da inserção no InfluxDB, é necessário converter entre os formatos \textit{Bytes} e \ac{JSON}; contudo, se uma fonte de dados produzir um valor do tipo \textit{Float} com parte decimal nula (por exemplo, \texttt{1.0}), este valor é convertido para \textit{Integer} após a conversão para formato \ac{JSON}, o que causa um erro de inserção na base de dados (que apenas aceita um \textit{Float} para aquele campo).
Apesar de reconhecer a existência de soluções conceptualmente mais robustas, como, por exemplo, a inclusão explícita do \textit{schema} na própria mensagem, a raridade deste erro dificultou a sua deteção precoce.
Por esta razão, os constrangimentos temporais tornaram necessária a adoção de uma solução mais pragmática: a adição de um valor decimal infinitesimal (inferior à margem de erro do próprio sensor) em todos os valores do tipo \textit{Float}, evitando assim que sejam convertidos para \textit{Integers}.

\subsection{Aplicação}

Para a aplicação, existem duas vertentes principais: a interação do aluno e a coordenação das fontes de dados.

\subsubsection{Interação do Aluno com a Aplicação}

Do ponto de vista da interação do aluno com a aplicação, a proposta inicial foi a implementação de uma aplicação sem interface que automaticamente iniciava a monitorização ao ser executada.
Contudo, durante a implementação foi considerado relevante permitir ao aluno escolher que sensores irá utilizar, o que não só permite evitar enviar dados desnecessários (como de digitação em sessões que não envolvam escrita), mas confere ao aluno a autonomia de recusar a recolha de determinados dados, permitindo-lhe salvaguardar as suas preferências de privacidade.
Para além da escolha das fontes de dados, a interface gráfica possui também um botão para manualmente começar ou interromper a sessão e um código de emparelhamento necessário para recolher dados de \textit{smartwatches}.

\subsubsection{Coordenação de Fontes de Dados}

Como a aplicação é, geralmente o único componente para além do \textit{dashboard} que possui obrigatoriamente processamento específico para cada fonte de dados, o foco principal na estratégia de desenvolvimento da coordenação de fontes de dados é minimizar o esforço de modificação para adicionar uma nova fonte de dados.

A principal decisão tomada para alcançar este objetivo foi isolar a lógica de recolha e processamento únicas a cada fonte de dados numa única classe por fonte (implementando todos uma interface comum), o que geralmente limita o esforço de recolher dados de uma nova fonte a adicionar ou modificar um único ficheiro.
Para facilitar ainda mais a compreensão da aplicação para indivíduos com menor experiência de programação, decidi utilizar o Python como linguagem de programação, por ser reconhecido como uma das linguagens de programação mais fáceis de aprender e compreender~\cite{John2025}.

\subsubsection{Problemas Encontrados}

O único problema encontrado durante a implementação da aplicação foi a utilização do Docker.
Apesar de ter sido prevista a utilização do Docker em ambos os componentes executados no computador do aluno para reduzir possíveis erros específicos ao ambiente de execução, algumas fontes de dados exigem acesso direto aos dispositivos, o que impede a utilização do Docker para a aplicação.
Contudo, foi utilizada uma abordagem híbrida: embora a aplicação seja executada nativamente para garantir o acesso direto, esta encarrega-se de iniciar e encerrar automaticamente o \textit{container} Docker do \textit{broker} local.




\subsection{Fontes de Dados}

Como referido anteriormente, foram escolhidos o teclado, câmara e \textit{smartwatch} para a recolha de dados, com base no seu valor demonstrativo para este trabalho.

\subsubsection{\textit{Smartwatch}}

Para a realização deste trabalho, foi disponibilizado um \textit{smartwatch} do modelo \textit{Xiaomi Watch 2}.
Apesar da versatilidade oferecida pelo sistema operativo \textit{WearOS}, que permite não só executar aplicações de terceiros mas também expõe uma interface para acesso a dados biométricos, um dos principais constrangimentos deste dispositivo é a inexistência de um protocolo de \ac{BLE} nativo~\cite{blexiaomi}.

Este protocolo foi a alternativa considerada inicialmente durante a conceção do trabalho, uma vez que não só é exposto sem a necessidade de criar uma aplicação para o \textit{wearable}, mas permite extrair dados de \textit{wearables} sem ecrã, como \textit{smartrings}.
Contudo, apesar da maioria dos \textit{wearables} implementarem \ac{BLE}, várias marcas optam por utilizar um protocolo proprietário que dificulta o seu uso por parte de terceiros.

Por esta razão, e tendo em conta a escolha do protocolo \ac{MQTT} para o \textit{broker} local, foi decidida a criação de uma aplicação para WearOS que envia os dados diretamente para o \textit{broker} local.
Para permitir a descoberta do \textit{broker}, e tendo em conta que esta descoberta é geralmente realizada apenas uma vez por aluno, decidi codificar o endereço num código de emparelhamento de 12 dígitos (utilizando Crockford Base 64 para evitar erros de inserção), que é inserido manualmente pelo aluno durante a primeira inicialização.

\subsubsection{Câmara}

A câmara foi escolhida como periférico por duas razões: por ser uma fonte de dados periódica, ou seja, que produz dados a um ritmo constante (ao contrário do teclado), mas também por produzir dados que necessitam ser processados antes de serem inseridos na base de dados.

Para a recolha destes dados, foi utilizada a biblioteca ``Mediapipe'', não só por se integrar diretamente no Python, mas também porque permitir a extração em tempo real de \textit{landmarks} faciais através de um modelo local (suportando um total de 478 pontos faciais), realizando assim de forma automática o primeiro passo no processamento: a transformação de uma imagem num conjunto de coordenadas.

Contudo, apesar de ser tecnicamente possível armazenar diretamente estes \textit{landmarks} na base de dados (ao atribuir um campo a cada ponto), os \textit{landmarks} faciais continuam a ser um dado sensível (por permitirem a reconstrução da face), exigindo por isso cuidados especiais para garantir a privacidade do aluno.
Por esta razão, e tendo em conta que os dados dos sensores têm um propósito meramente demonstrativo, foi adotada uma política de ``privatização na fonte'', calculando as métricas (orientação facial e \ac{EAR}) diretamente na aplicação e enviando apenas estes dados, mitigando assim problemas com privacidade.

\subsubsection{Teclado}

Finalmente, como ambas as fontes de dados anteriores possuem uma natureza periódica, ou seja, produzem amostras a uma frequência constante, decidi também recolher dados do teclado pela sua natureza aperiódica, já que é apenas produzindo um valor quando o aluno pressiona uma tecla, sendo por isso a frequência de amostragem não só irregular, mas também uma das métricas para análise.

Em termos de privacidade, apesar do teclado não permitir identificar diretamente o indivíduo, ao contrário da câmara, os dados de digitação puros continuam a ser dados altamente sensíveis, pois não só permitem monitorizar conversas privadas, mas também extrair credenciais como palavras-passe.
Felizmente, como o objetivo geral é monitorizar a dinâmica de digitação em si e não o conteúdo do texto, é possível anonimizar os dados ao atribuir uma categoria a cada tecla (alfanumérico, caractere especial, \textit{whitespace} ou \textit{delete/backspace}). 
Esta abordagem foi considerada suficiente, pois evita a reconstrução do conteúdo digitado sem afetar o cálculo de métricas como velocidade de digitação.

\subsection{Visualização}

Finalmente, para o \textit{dashboard} utilizado pelo tutor foi escolhido o Grafana, pela sua facilidade de uso e compatibilidade com o InfluxDB.
O \textit{dashboard} utiliza o InfluxDB como fontes de dados primária e permite não só visualizar métricas já calculadas, como o \ac{BPM}, mas também permite realizar calcular dinamicamente novas métricas, como o \ac{CPM}.

\section{Discussão}

Como o objetivo principal deste trabalho era servir como prova de conceito que fundamente a viabilidade do paradigma \textit{streaming} para cenários de monitorização contínua de múltiplos utilizadores durante o uso normal do computador, é necessário não só demonstrar a operabilidade prática, mas também avaliar em que medida esta prova de conceito fundamenta a viabilidade do paradigma de \textit{streaming} e das tecnologias existentes no cenário descrito.

\subsection{Agnosticismo no Servidor}
\label{sec:discussion_agnostic}

A decisão de manter o servidor agnóstico ao número de fontes de dados e as suas características, sendo conhecidos apenas pela aplicação e pelo \textit{software} de visualização, permitiu que a adição de um novo sensor se limitasse à aplicação, na qual é necessário apenas criar uma nova classe e inserir o respetivo ficheiro na pasta correspondente, e ao \textit{software} de visualização.
Esta propriedade pode ser comprovada através da análise dos próprios componentes, onde as únicas referências às três fontes de dados (teclado, câmara e \textit{smartwatch}) em código se encontram nestes componentes (e na aplicação para WearOS), apesar de cada fonte de dados possuir características e métricas diferentes.

Contudo, esta escolha tem um custo direto: como o servidor desconhece a natureza dos dados que transporta, não é possível estabelecer fluxos de processamento distintos para cada fonte de dados sem violar este princípio de agnosticidade, sendo por isso necessário realizar o processamento na aplicação ou de forma dinâmica durante a visualização.
O erro de conversão apresentado na Secção~\ref{sec:final_state_server} é, de certa forma, uma consequência indireta desta limitação, pois, como o Kafka Connect desconhece que dados estão a ser transportados, necessita inferir os seus tipos com base nas mensagens, cuja ambiguidade leva a erros pontuais na inserção.

\subsection{Reutilização de Ferramentas Estabelecidas}

Como o objetivo principal do trabalho não é demonstrar a minha capacidade de implementar um sistema de monitorização contínua de raiz, mas sim demonstrar a viabilidade do \textit{streaming} como paradigma, o que exige demonstrar que as tecnologias e protocolos de \textit{streaming} já existentes são capazes de realizar esta monitorização contínua.

Esta decisão de priorizar soluções já existentes para a resolução de problemas traduziu-se, por exemplo, na ausência de \textit{workers} de transporte construídos de raiz: optando por resolver os problemas de encaminhamento entre o \textit{broker} local e o servidor através do mecanismo \ac{MQTT} Bridge e a interação com o Kafka através do Kafka Connect.

O custo principal desta decisão foi a necessidade de implementar componentes adicionais, como o \textit{broker} remoto, que não seria necessário se um \textit{worker} consumisse os dados do \textit{broker} local e os enviasse diretamente para o Kafka, bem como a exposição às restrições associadas ao funcionamento das próprias ferramentas (por exemplo, o conector \textit{source} \ac{MQTT}, apesar de ser capaz de consumir de múltiplos tópicos \ac{MQTT} através do uso de \textit{wildcards}, apenas consegue inserir num único tópico Kafka).

\subsection{Privatização na Fonte}

A decisão de calcular as métricas referentes aos dados faciais e à atribuição de categorias às teclas premidas, evitando assim a transmissão de dados sensíveis de alto risco como \textit{landmarks} faciais ou texto digitado, bem como a opção da identificação de cada utilizador somente através de um \ac{UUID} aleatório gerado durante a primeira recolha, responde diretamente a uma das barreiras à adoção deste tipo de monitorização identificadas na literatura (Secção~\ref{sec:soa_data_sources}).
Esta abordagem tira partido da limitação de processamento referida na Secção~\ref{sec:discussion_agnostic}, que incentiva o processamento na fonte, para eliminar o maior risco de segurança neste tipo de sistemas (a recolha de dados sensíveis e o risco do acesso indevido ao mesmo) e, no caso da câmara, reduzir drasticamente o volume de dados transmitidos (reduzindo de 478 pares de valores, no caso do Mediapipe, para apenas 3 métricas).

Contudo, esta escolha tem dois impactos principais: a delegação do processamento para o cliente não só aumenta o consumo de recursos, mesmo que não de forma drástica, mas também implica que os dados estão disponíveis apenas como métricas finais, ou seja, se for necessário ajustar ou alterar as métricas a monitorizar, todos os dados históricos terão de ser descartados por ainda utilizarem as métricas antigas.

\subsection{Heterogeneidade das Fontes de Dados}

A escolha de fontes de dados com comportamentos diferentes permitiu demonstrar a capacidade do sistema para lidar com fontes de dados periódicas e aperiódicas, bem como internas e externas.

Contudo, apesar de demonstrar a integração com \textit{smartwatches} WearOS através de \ac{MQTT}, esta não garante compatibilidade do sistema com todos os dispositivos \textit{wearable off-the-shelf}, como, por exemplo, \textit{smartrings} que comunicam geralmente via \ac{BLE} ou \textit{smartwatches} com outros sistemas operativos, onde a execução de aplicações de terceiros é mais complexa ou até mesmo impossível.

\subsection{Limitações Gerais}

Para além das limitações acima descritas, este trabalho apresenta um conjunto de limitações que decorrem diretamente do seu caráter de prova de conceito e dos constrangimentos temporais associados:
\begin{itemize}
    \item O sistema foi avaliado por um único utilizador (o próprio autor) num cenário unipessoal, sendo por isso a \textit{performance} em escala baseada numa estimativa de carga e com base nas características individuais das próprias ferramentas e não em testes de carga empíricos
    \item Não foi medida de forma automática a latência entre a produção dos dados e o seu armazenamento e visualização. Consequentemente, não foi verificado o possível impacto da distância física entre cliente e servidor no tempo de propagação das mensagens
    \item A avaliação da extensibilidade do sistema foi baseada no isolamento estrutural da alteração, reduzindo ao máximo a quantidade de código e componentes a serem revistos, e não a testes reais envolvendo utilizadores com diferentes níveis de experiência em programação
    \item Embora a privatização dos dados ter reduzido drasticamente os riscos de segurança inerentes ao sistema, reconheço que deveria ter implementado melhores mecanismos de segurança e controlo de acesso, nomeadamente ao nível da autenticação e de controlo de acesso ao \textit{broker} remoto. Estas questões foram ponderadas durante o desenho do sistema, mas a sua implementação efetiva acabou por ser deliberadamente omitida face aos constrangimentos temporais da prova de conceção, constituindo uma lacuna relevante para a robustez da solução fora de um ambiente controlado
\end{itemize}
