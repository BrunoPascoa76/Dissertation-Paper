\chapter{Arquitetura}
\label{chap:arquitetura}

\begin{introduction}
Este capítulo descreve o cenário representativo (monitorização de um aluno durante uma sessão de tutoria), apresenta uma arquitetura lógica baseada na \ac{UDI 2.0} e apresenta finalmente as ferramentas e protocolos escolhidos para implementar este cenário.
\end{introduction}

\section{Cenário de Referência}\label{sec:scenario_arquitecture}

Como referido na Secção~\ref{sec:scenario_introduction}, o cenário de referência adotado para orientar o desenvolvimento do trabalho é a monitorização de um aluno durante uma sessão de tutoria individual, enquanto este realiza tarefas ou exercícios no computador (ou seja, durante a interação com o computador).

Os atores principais neste cenário são o próprio aluno, que será monitorizado e o tutor, que tem interesse em visualizar as métricas que resultam dessa monitorização.
Apesar do cenário referir que apenas um aluno será monitorizado por sessão, o trabalho tem em consideração que diferentes alunos poderão ser lecionados em cada sessão e cada aluno poderá ter mais que uma sessão com o mesmo tutor.

Em termos de fontes de dados para monitorização, foram escolhidos o teclado (caracteres por minuto) e câmara (orientação facial e \ac{EAR}) com interfaces do computador e um \textit{smartwatch} (\ac{BPM}) como fonte de dados externa.
Estas métricas serão disponibilizados através de um \textit{dashboard}, integrando dados em tempo real e históricos para ajudar o tutor a avaliar a qualidade do ensino não só da sessão atual, mas também ao longo de várias sessões.

\section{Mapeamento do Cenário com base na \ac{UDI 2.0}}

De modo a orientar a criação de uma arquitetura lógica, decidi utilizar como base a \ac{UDI 2.0}, mapeando este cenário nos blocos lógicos e fluxos desta arquitetura genérica.

Em primeiro lugar, as fontes de dados principais são as descritas anteriormente: o teclado, que produz um evento sempre que uma tecla é premida (sendo enviado o tipo de tecla premida), a câmara que envia métricas referentes à orientação facial e à abertura dos olhos e um \textit{smartwatch}, que fornece dados referentes à frequência cardíaca (\ac{BPM}).

A seguir, como existe uma separação física entre aluno e tutor, é necessário ingerir e transportar estes dados. Apesar das sessões de tutoria terem geralmente uma duração fixa (constituindo cada sessão um conjunto de dados temporalmente limitado), estes dados são analisados durante a própria sessão, o que justifica a necessidade de os ingerir de forma contínua.
No contexto da \ac{UDI 2.0}, a ingestão contínua é mapeada no bloco lógico \textit{Event Streaming}.

Em termos de persistência, apesar de algumas ferramentas de ingestão contínua (particularmente, as baseadas em \textit{logs}), manterem um registo do histórico de mensagens, não é considerado viável utilizar estas ferramentas como fontes de dados para visualização, uma vez que estas ferramentas geralmente não dispõem de mecanismos eficientes de filtragem com base no conteúdo (por exemplo, para visualizar o \ac{BPM} de um determinado aluno ao longo da sessão).
Por esta razão, torna-se necessário utilizar uma fonte de persistência separada que seja otimizada para análise em tempo real, ou seja, uma \textit{Real-time Analytics Database}.

Em termos de processamento e transformação, não foram selecionados blocos lógicos para estas camadas, uma vez que não está planeado o desenvolvimento de um modelo de inteligência artificial (que justificaria a transformação) nem se consideram necessário processamento adicional antes da inserção (o que justificaria \textit{Stream Processing}).

Finalmente, em termos de visualização, como neste cenário o único requisito para a interface do tutor é permitir observar as métricas de um aluno e a sua evolução, sendo a comunicação entre ambos realizada através das ferramentas habituais, foi considerado suficiente o uso de um \textit{Dashboard} para a visualização dos dados.

Em suma, podemos estabelecer o seguinte fluxo: os dados são recolhidos e pré-processados na fonte, transportados através de uma ferramenta de \textit{Event Streaming}, inseridos numa \textit{Real-time Analysis Database} e finalmente visualizados pelo tutor através de um \textit{Dashboard}.


\section{Requisitos}

Com base no cenário de tutoria descrito e na arquitetura lógica apresentada acima, foram estabelecidos os seguintes requisitos para a solução desenvolvida:
\begin{itemize}
    \item \textbf{Identificação de cada aluno:} o sistema tem de identificar de forma única o aluno (ou computador) do qual originaram os dados, de modo a permitir distinguir entre diferentes alunos ou agrupar os dados de várias sessões.
    \item \textbf{Suporte para teclado, câmara e \textit{smartwatch}:} o sistema tem de suportar, no mínimo, a recolha de dados do teclado, câmara e de um \textit{smartwatch}.
    \item \textbf{Suporte para análise em tempo real:} o sistema tem de permitir ao tutor observar mudanças nas métricas recolhidas em tempo real.
    \item \textbf{Armazenamento e análise de dados históricos:} o sistema tem de reter os dados após o término da sessão de modo a permitir a consulta de sessões passadas.
\end{itemize} 

Adicionalmente, e de forma a permitir expandir a abrangência deste trabalho a outros cenários, foram também estabelecidos os seguintes objetivos secundários:
\begin{itemize}
    \item \textbf{Suporte para múltiplos utilizadores em simultâneo:} o sistema deve suportar a recolha de dados de múltiplos indivíduos em simultâneo.
    \item \textbf{Suporte para a adição de novos sensores:} o sistema deve facilitar a adição de suporte para outras interfaces do computador ou \textit{wearables off-the-shelf} para além dos mencionados acima.
\end{itemize}

\section{Escolhas na Implementação do Cenário}

\subsection{Tecnologias Escolhidas}
\label{sec:chosen_technologies}

Após o estabelecimento dos blocos lógicos do sistema, torna-se necessário escolher as tecnologias e fontes de dados apropriados para este sistema.

Em primeiro lugar, para a concretização do \textit{Event Streaming}, foi escolhido o Apache Kafka, não só pela sua escalabilidade e resiliência a falhas~\cite{Kafka2011}, mas também pelo facto que, através do Kafka Connect, é possível comunicar com um elevado número de outros sistemas~\cite{kafka_connect_docs}.

A seguir, como a maioria das fontes de dados não consegue comunicar diretamente com o Kafka, torna-se necessário o uso de uma aplicação que corra no computador do aluno para coordenar a recolha destes dados, permitindo assim também o pré-processamento de dados na própria fonte.
De modo a evitar a perda de dados após uma interrupção temporária de conexão, foi também explorado um mecanismo de redirecionamento assíncrono utilizando \ac{MQTT} \textit{Bridge}, um método que permite o redirecionamento assíncrono e automático entre dois \textit{message brokers} \ac{MQTT} - um local e um remoto - sem infringir nas garantias de entrega.
Para além de explorar este mecanismo de redirecionamento contínuo, o \ac{MQTT} foi também escolhido por ser um protocolo suficientemente leve~\cite{amqp_mqtt_definitions} para não impactar visivelmente a \textit{performance} do computador do aluno.

Em termos de \textit{Real-Time Analytics Database}, foi escolhido a utilização de uma \ac{TSDB} (sendo a implementação específica de \ac{TSDB} comparativamente menos relevante).
Esta escolha baseia-se principalmente em duas razões: como a análise esperada baseia-se em séries temporais, o principal critério de pesquisa será o tempo (seguido do utilizador e finalmente do sensor e métrica), o que favorece a escolha de uma \ac{TSDB}, que são especificamente otimizadas para \textit{queries} temporais.
Adicionalmente, apesar de uma base de dados \ac{OLAP} ser possivelmente uma escolha mais adequada para um volume elevado de registos (milhões ou biliões)~\cite{Brown2026}, a análise prevista para este cenário foca-se maioritariamente na análise por aluno, logo, o volume de dados previsto não justifica a adoção de uma base de dados \ac{OLAP}.

Finalmente, a comunicação entre estes três componentes - \textit{broker} remoto, Kafka e \ac{TSDB} - será assegurada através de dois conectores de Kafka Connect: um conector \textit{source} para consumir os dados do \textit{broker} local e um conector \textit{sink} para inserir estes dados na \ac{TSDB}.
A escolha do Kafka Connect permite não só explorar tecnologias já existentes e as suas vantagens e limitações - ao contrário de um \textit{worker} criado de raiz - mas também porque o uso de conectores introduz uma camada de abstração que separa a configuração do fluxo de dados da lógica de conversão específica a cada ferramenta, facilitando assim a substituição de componentes.

\subsection{Fontes de Dados Escolhidas}

Como o propósito principal deste trabalho não é o desenvolvimento de uma solução comercial viável, mas sim na demonstração da viabilidade de uma abordagem baseada em \textit{streaming} num cenário de monitorização contínua durante o uso do computador, a escolha das fontes de dados (teclado, câmara e \textit{smartwatch}) não se baseou necessariamente na sua taxa de precisão ou na sua popularidade na literatura científica, mas sim na sua utilidade demonstrativa:
\begin{itemize}
    \item O \textit{smartwatch} produz dados de natureza fisiológica (\ac{BPM}) e demonstra a integração de fontes de dados externas.
    \item A câmara produz dados audiovisuais e favorece o processamento das imagens na fonte (não só por questões de privacidade, mas também porque se considera que o transporte e armazenamento a longo prazo de até 60 imagens por segundo é extremamente ineficiente para este caso de uso).
    \item Finalmente, o teclado produz dados referentes à dinâmica de interação e é uma das únicas fontes de dados consideradas que produz dados com base em eventos e não através de amostragem, sendo a frequência de envio variável e dependente da velocidade de digitação do próprio indivíduo.
\end{itemize}

\subsection{Fluxo de Dados}
\label{sec:flow_technologies}

    De modo a permitir visualizar o funcionamento do sistema e a sua utilidade no cenário, é apresentado nesta secção o fluxo de dados, com base numa situação representativa em que o aluno apresenta dificuldades numa das questões, restringindo-me ao \ac{BPM} por uma questão de simplicidade (uma vez que o fluxo dos dados após inserção no \textit{broker} local é idêntico para todos os sensores).

    \begin{enumerate}
        \item O aluno e o tutor iniciam a sessão de tutoria.
        \item O aluno começa a responder às questões apresentadas, mas não consegue responder à última pergunta.
        \item O stresse causado pela dificuldade em responder leva a um aumento da frequência cardíaca (\ac{BPM}).
        \item O novo valor de \ac{BPM} é extraído do \textit{smartwatch} e inserido no \textit{broker} local.
        \item A mensagem é redirecionada para o \textit{broker} remoto através de \ac{MQTT} \textit{bridging}.
        \item A mensagem é inserida num tópico Kafka via Kafka Connect.
        \item O novo valor é inserido na \ac{TSDB} via Kafka Connect.
        \item O \textit{dashboard} é atualizado com os novos dados e reflete o aumento do \ac{BPM}.
        \item O tutor observa o \textit{dashboard} e apercebe-se do aumento do valor de \ac{BPM}.
        \item O tutor chega à conclusão que o aluno deve estar a ter dificuldade com alguma pergunta e oferece ajuda.
    \end{enumerate}
