\section{Impacto dos objetivos na arquitetura}

Os objetivos definidos na secção~\ref{sec:objectives} estabelecem um conjunto de requisitos sobre a arquitetura do sistema:
\begin{itemize}
    \item A necessidade de recolher dados de vários utilizadores motiva uma estrutura cliente-servidor. Adicionalmente, a necessidade de recolher dados de vários sensores para um mesmo utilizar favorece a agregação e coordenação desses dados do lado do cliente.
    \item A necessidade de suportar a adição de novos sensores com esforço de integração reduzido e localizado, motivam a separação do sistema em duas subsistemas: um servidor agnóstico às características do sensor, que se mantém constante independentemente do caso de uso e um cliente que é adaptado consoante as necessidades desse caso de uso.
    \item O incentivo a facilitar a modificação do cliente para adicionar mais sensores favorece a adoção de uma estrutura modular com baixo acoplamento com os sensores (como um sistema de \textit{plugins}).
\end{itemize}

O sistema presente na Figura~\ref{fig:sys_arq} possui uma arquitetura descentralizada à base de eventos, que pode ser divido em 2 secções: \textbf{componentes locais} (que são executados no computador ou wearable do próprio utilizador) e \textbf{componentes externos} que serão executados de forma remota num servidor ou na cloud.

\begin{itemize}
    \item \textbf{Componentes locais:}
    \begin{itemize}
        \item \textbf{App para \textit{Desktop}:} Esta app feita em Python será o principal ponto de acesso por parte do utilizador e permitirá ao utilizador não só controlar todos os sensores de forma centralizada (iniciar ou parar uma sessão e definir que sensores serão utilizados em cada sessão), mas também ver os valores medidos pelos sensores e a evolução do seu nível de atenção ao longo de cada sessão.
        \item \textbf{\textit{Plugins} para sensores locais:} Cada sensor presente no computador do utilizador (teclado e câmara) terá o seu próprio \textit{plugin} responsável por recolher os dados do respetivo sensor, remover informação irrelevante e enviar as medições para o Kafka. Estes \textit{plugins} serão controlados diretamente pelo utilizador através da app.
        \item \textbf{\textit{Broker} MQTT local:} Este broker irá correr localmente no computador do próprio utilizador e servirá não só como meio de comunicação entre os sensores e o programa principal, mas também servirá como \textit{buffer} dos dados, permitindo o envio eventual dos dados, mesmo que o \ac{MQTT} remoto esteja em baixo.
        \item \textbf{App para \textit{WearOS}:} Esta app em Kotlin permitirá a medição de \ac{BPM} e o envio destes para o \textit{broker} \ac{MQTT} local.
    \end{itemize}
    \item \textbf{Componentes externos:}
    \begin{itemize}
        \item \textbf{\textit{Broker} MQTT remoto:} Serve como intermediário entre o cliente e o Kafka. A adição deste componente melhora a escalabilidade e a segurança do sistema ao evitar que cada cliente necessite de estabelecer conectores entre o broker local e o Kafka.
        \item \textbf{Kafka Connect:} O Kafka Connect estabelece conectores entre o broker \ac{MQTT} remoto e o Kafka, bem como a exportação destes dados para  a base de dados, permitindo uma ingestão automática e agnóstica ao tipo de sensor.
        \item \textbf{Kafka:} O Kafka permite gerir o fluxo de dados entre os plugins e os respetivos consumidores, garantindo a entrega de mensagens de forma escalável e com uma persistência de dados melhor que o padrão \ac{MQTT}, levando a uma melhor tolerância a falhas ou atrasos.
        \item \textbf{InfluxDB:} Base de dados \textit{Time Series} onde os dados são armazenados após serem processados e alimenta a app para \textit{desktop}. InfluxDB em particular foi escolhido visto ser a base de dados Time Series com a melhor documentação e suporte que encontrei até agora.
        \item \textbf{API REST:} API FastAPI que regula o acesso à base de dados e evita injeção de \textit{queries}. Utiliza parâmetros para a construção da \textit{query}, permitindo versatilidade sem por em risco a segurança do sistema.
    \end{itemize}
\end{itemize}

\section{Fluxo de Dados}

De modo a ilustrar como estes componentes comunicam entre si, a Figura~\ref{fig:end2end} mapeia o fluxo de dados \textit{end-to-end}, utilizando como exemplo os dados faciais obtidos via \textit{webcam}:

\begin{enumerate}
    \item \textbf{Captura e ingestão:} O \textit{plugin} da \textit{webcam} presente na aplicação \textit{desktop} captura uma \textit{frame} e extrai as \textit{features} faciais (utilizando a biblioteca MediaPipe). Essas \textit{features} são convertidas em métricas (de modo a reduzir o volume de dados a enviar) e enviadas para o \textit{broker} Mosquitto local.
    \item \textbf{Redirecionamento:} Os dados presentes no broker local (em tópicos com o prefixo \texttt{sensors/}) são redirecionados para um \textit{broker} remoto automaticamente.
    \item \textbf{Transporte:} Após a chegada de novos dados ao \textit{broker}, o conector \textit{source} do Kafka Connect recolhe estes dados e insere-os no Kafka (que possui melhor resiliência que o Mosquitto, permitindo ingestão assíncrona).
    \item \textbf{Armazenamento:} Após a inserção no Kafka, um segundo conector \textit{sink} de Kafka Connect consome as mensagens e armazena-as na base de dados.
    \item \textbf{Acesso e visualização:} Após o armazenamento dos dados, estes são acedidos via API REST pela app \textit{desktop} a cada segundo para gerar uma visualização dos dados.
\end{enumerate}

\section{Especificação do Protocolo de Ingestão}

O ponte de entrada principal para a ingestão de mensagens é o \textit{broker} \ac{MQTT} remoto (ou o local no caso da app para \textit{Desktop}). De modo a permitir que a mensagem seja corretamente ingerida, a mensagem deverá ser publicada para um tópico com o prefixo \texttt{/sensors/} (por exemplo, \texttt{/sensors/face}), e o corpo da mensagem deverá utilizar o formato /ac{JSON} e seguir a seguinte estrutura:
\begin{itemize}
    \item \textbf{\ac{UUID}:} cada mensagem tem de conter o \ac{UUID} correspondente ao utilizador ao qual os dados correspondem.
    \item \textbf{\textit{timestamp}:} este campo corresponde ao tempo (em milisegundos) em que o valor foi registado. 
    \item \textbf{\textit{sensor}:} o nome do sensor que gerou os dados
    \item \textbf{\textit{message\_id}:} campo opcional que permite fazer o \textit{tracing} de uma mensagem
    \item \textbf{valores:} todos os campos com exceção aos de cima são considerados como valores. Estes valores não poderão ser coleções e o tipo de dados de cada campo deve ser consistente dentro do mesmo tipo de sensor.,
\end{itemize}

\section{Acesso aos Dados}
\label{sec:rest_definition}

O acesso da base de dados por parte dos clientes é gerido por uma API REST simples (escrita em FastAPI). O endpoint principal desta API é \texttt{/data/{sensor}}, que constroi uma \textit{query} para um sensor específico a partir dos seguintes parâmetros:
\begin{itemize}
    \item \textbf{start e end}: janela temporal, em ms, para a qual queremos obter os dados.
    \item \textbf{uuid}: o \ac{UUID} do utilizador a que pertecem os dados.
    \item \textbf{agg}: o tipo de agregação (opcional) (MEAN, COUNT, SUM, MIN, MAX). Por defeito (ou se utilizar NONE), os valores não são agregados.
    \item \textbf{field}: o campo (ou campos, separados por vírgula) a retornar. O valor por defeito é \texttt{value}.
    \item \textbf{interval}: o intervalo de tempo (opcional) para agregação (deverá incluir o valor e a unidade de tempo, por exemplo \texttt{1s}). Se omitido os valores não são agregados por tempo.
\end{itemize}
O uso desta API e de parâmetros evita que agentes externos tenham acesso à base de dados, reduzindo por isso o risco de vulnerabilidades.
