\section{Requisitos e o seu Impacto na Arquitetura}

\subsection{Objetivos e Requisitos}

Como descrito na Secção~\ref{sec:objectives}, os objetivos principais para este trabalho são:
\begin{itemize}
    \item Demonstrar a exequibilidade do paradigma de \textit{streaming}
    \item Integrar fontes de dados fundamentadas na literatura
    \item Ilustrar a monitorização em tempo real
    \item Projetar uma arquitetura modular
\end{itemize}

Tendo em conta estes objetivos para este trabalho, decidi estabelecer os seguintes requisitos para o sistema:
\begin{itemize}
    \item \textbf{Suporte para recolha de dados de múltiplos utilizadores em simultâneo:} de modo a cumprir com o cenário estabelecido, o sistema tem de ser projetado para receber dados de vários clientes em simultâneo
    \item \textbf{Suporte para o uso de múltiplos periféricos e dispositivos \textit{wearable off-the-shelf}}: o sistema tem de ser capaz de ingerir dados de periféricos (teclado e câmara) e de dispositivos \textit{wearable off-the-shelf} (\textit{smartwatch wearOS}) para um mesmo utilizador.
    \item \textbf{Suporte para ferramentas de visualização:} de modo a permitir a visualização dos dados (em tempo real ou históricos), o sistema tem de ser capaz de integrar \textit{software} de visualização
    \item \textbf{Suporte à adição de sensores:} devido à diversidade de casos de uso dentro do cenário indicado, o sistema tem de ser capaz de permitir que novos \textit{wearables} ou periféricos sejam adicionados e que novas métricas sejam extraídas com base nas necessidades específicas.
\end{itemize}

\subsection{Fundamentação e Racional da Arquitetura}

Com base nestes requisitos, e nos objetivos para este trabalho, posso deduzir uma visão geral da arquitetura.

Em primeiro lugar, a necessidade de recolher dados de múltiplos utilizadores em simultâneo torna inconveniente o armazenamento destes dados de forma local, exigindo por isso um servidor capaz de armazenar estes dados num único local.
Contudo, como é também necessário suportar várias fontes de dados para cada utilizador, sendo muitas delas incapazes de enviar os dados autonomamente para o servidor, torna-se também necessário um cliente que coordene estas fontes de dados.
Estabelece-se assim uma arquitetura baseada em dois subsistemas: um subsistema local, executado no computador de cada utilizador e responsável pela coordenação dos sensores e pela recolha de dados e um subsistema remoto partilhado, executado num servidor e responsável pelo transporte, armazenamento e visualização destes dados.

Com base nesta divisão, a responsabilidade de interagir diretamente com os sensores recai unicamente no cliente, sendo o servidor responsável apenas por interagir com as mensagens enviadas pelo cliente. 
Logo, como o sistema necessita de suportar a adição de novos sensores, torna-se vantajoso manter o servidor agnóstico à tipologia das fontes de dados ao utilizar um fluxo único de dados independentemente da sua origem porque assim o esforço de adição de novos sensores limita-se apenas ao cliente e ao \textit{software} de visualização, mantendo inalterado o \textit{pipeline} de transporte.
Contudo, esta decisão tem como consequência o facto de, como o servidor desconhece a origem e natureza específica dos dados, o servidor perde a capacidade de estabelecer fluxos de processamento separados para cada fonte de dados, sendo por isso necessário realizar operações como o cálculo de métricas no próprio \textit{software} de visualização (ou, em certos casos, no próprio cliente).

Finalmente, como o objetivo deste trabalho não é apenas desenvolver uma solução funcional, mas sim demonstrar a viabilidade do \textit{streaming} neste cenário de monitorização contínua, decidi também evitar a resolução de problemas através do desenvolvimento de raiz em prol do uso de soluções de \textit{streaming} pré-existentes.

\section{Arquitetura Lógica}

Apesar dos requisitos fundamentarem uma arquitetura em dois subsistemas, de modo a melhor visualizar o fluxo de dados, torna-se necessário decompor estes subsistemas numa arquitetura lógica baseada em componentes.

Ao nível do cliente, o componente central é uma aplicação responsável por extrair os dados dos sensores e enviá-los para o servidor.
Contudo, prevendo a possibilidade de falhas temporárias na conexão ao servidor, torna-se também necessário criar um \textit{buffer} para evitar a perda de dados.
Apesar de ser possível criar um \textit{buffer} interno à própria aplicação, decidi utilizar um \textit{message broker} local leve separado porque assim posso-o utilizar não só como \textit{buffer} mas também como intermediário na comunicação com dispositivos \textit{wearable} para os periféricos do computador, mas também como intermediário na comunicação e recolha de dados de dispositivos \textit{wearables}.

Ao nível do servidor, o elemento central é uma \textit{pipeline} de transporte de dados.
Contudo, apesar de ser teoricamente possível visualizar os dados diretamente da \textit{pipeline}, a criação de um base de dados como motor de persistência permite também enriquecer estes dados em tempo real com dados históricos, permitindo assim distinguir entre tendências regulares e eventos pontuais.
Finalmente, antevendo a possibilidade de integração com sistemas externos de análise, decidi também adicionar uma interface que uniformize a consulta dos dados armazenados, com a intenção de facilitar o estabelecimento de regras de acesso aos dados.

\section{Fluxo Conceitual}

Com base nesta arquitetura de componentes, podemos já estabelecer um fluxo inicial para os dados baseada em 3 etapas:
\begin{enumerate}
    \item \textbf{Captura e Ingestão:} os dados gerados pelas fontes de dados são recolhidos pela aplicação e enviados para o \textit{broker local}
    \item \textbf{Redirecionamento:} de forma assíncrona, os dados do \textit{broker} local são enviados para o \textit{pipeline} do servidor
    \item \textbf{Transporte e Armazenamento:} estes dados são transportados ao longo do \textit{pipeline} e inseridos na base de dados
\end{enumerate}

\section{Tecnologias Escolhidas}

Após o estabelecimento dos blocos lógicos do sistema, torna-se necessário escolher as tecnologias e fontes de dados apropriados para este sistema.

Em primeiro lugar, como elemento central da \textit{pipeline} de recolha de dados, decidi escolher o Apache Kafka, não só pela sua escalabilidade e resiliência a falhas~\cite{Kafka2011}, mas também pelo facto que, através do Kafka Connect, é possível comunicar com um elevado número de outros sistemas~\cite{kafka_connect_docs}.

Em segundo lugar, para o \textit{broker} local, por não necessitar de funcionalidades avançadas, decidi utilizar um \textit{broker} que utilize o protocolo \ac{MQTT}.
Esta escolha baseou-se na leveza do protocolo, permitindo ser executado sem impacto no trabalho mesmo em computadores com recursos limitados~\cite{amqp_mqtt_definitions}, como \textit{Chromebooks} (que são por vezes utilizados em cenários em que a computação real é feita através de acesso remoto a um computador da empresa).

Para conectar estes dois serviços, apesar de ter inicialmente considerado criar um \textit{worker} local utilizando código de raiz, como um dos objetivos é demonstrar a exequibilidade do paradigma de \textit{streaming}, decidi optar por utilizar soluções de \textit{streaming} já existentes.
Por esta razão decidi utilizar o Kafka Connect como método de ligação entre serviços, já que o próprio integra-se diretamente no \textit{cluster} Kafka.

Contudo, apesar de ser teoricamente possível conectar o \textit{broker} local diretamente ao Kafka via Kafka Connect, esta abordagem não só traria possíveis problemas de escalabilidade, mas também esta ligação poderia ser bloqueada por uma \textit{firewall} (especialmente no caso de trabalhadores remotos, em que a empresa não consegue manipular a \textit{firewall} para permitir o acesso).
Por esta razão, decidi optar por implementar um \textit{broker} \ac{MQTT} remoto (sendo que escolhi especificamente um segundo \textit{broker} Dummy38, pois o mecanismo de \ac{MQTT} \textit{Bridging} permite o redirecionamento automático entre \textit{brokers} \ac{MQTT} sem quebrar as garantias de entrega).
Adicionalmente, uma vantagem secundária desta estrutura é que, apesar desta prova de conceito focar-se numa relação 1:1 entre o \textit{broker} remoto e o Kafka, esta arquitetura suporta naturalmente uma relação N:1, permitindo, por exemplo, a empresas com vários escritórios agrupar utilizadores pela sua localização fixa, ao instalar um \textit{broker} \ac{MQTT} em cada escritório utilizando o mesmo endereço IP local.

Finalmente, para armazenamento de dados, decidi optar por uma \ac{TSDB}, pois, como descrito em detalhe na Subsecção~\ref{sec:technologies_storage}, este tipo de base de dados foi desenhado especificamente para armazenar e aceder a dados indexados no tempo, como dados de sensores (sendo que a maioria dos casos não requer o tipo de análise textual que justificaria um motor de busca como ElasticSearch).
De modo a permitir a consulta de dados por serviços externos, considerei também útil desenvolver uma API de acesso simples, sendo que decidi optar por uma interface baseada em REST (em vez de um mecanismo que permita o acesso direto de forma segura), pois não só facilita a implementação de mecanismos de acesso granulares (por comunicar utilizando o padrão HTTP), mas também porque serve como camada de abstração, reduzindo assim o esforço de transição para uma nova base de dados.

\section{Fontes de Dados Escolhidas}

Apesar das fontes de dados escolhidas terem como propósito principal permitir demonstrar o sistema em funcionamento utilizando dados reais (visto que um dos requisitos exige que o sistema seja capaz de suportar a adição de novos sensores), a escolha deliberada das fontes de dados continua a ser uma escolha importante, por terem ainda impacto na arquitetura (por exemplo, na escolha do protocolo de comunicação com o dispositivo \textit{wearable}).
Como objetivo deste trabalho não é alcançar previsões analíticas de alta precisão, a seleção não recaiu sobre combinações utilizadas frequentemente na literatura, mas sim na escolha de fontes com características heterogéneas, de modo a maximizar o seu valor demonstrativo.

Como fonte de dados externa (\textit{wearable}), decidi escolher um \textit{smartwatch} WearOS.
Esta escolha baseou-se maioritariamente na abertura deste sistema operativo para a integração de \textit{software} externo e pelo seu suporte de comunicação utilizando o protocolo \ac{MQTT}, permitindo assim utilizar o \textit{broker} local não só como fonte de comunicação, mas também como intermediário na comunicação entre o computador e o \textit{smartwatch}.

Em termos de periféricos, decidi escolher o teclado e a câmara devido ao seu diferente comportamento de emissão: por um lado, a câmara produz geralmente dados numéricos (\textit{landmarks}) com uma frequência fixa (produzindo geralmente até 60 amostras por segundo); por outro lado, o teclado produz geralmente dados categóricos (o tipo de tecla premida) com uma frequência variável (enviando dados apenas após a ocorrência de um novo evento).

\section{Fluxo de Dados}

Para além da escolha de cada tecnologia influenciar a escolha das restantes, as tecnologias escolhidos tiveram também impacto no fluxo dos dados, sendo importante redesenhar o fluxo de dados com base nesta escolha (Figura~\ref{fig:end2end_technology}).
De modo a facilitar a interpretação, decidi restringir a análise do fluxo de dados a um cenário de monitorização utilizando apenas uma \textit{webcam}:

\begin{itemize}
   \item \textbf{Recolha de dados:} Os dados são recolhidos pela aplicação, pré-processados (se necessário) e inseridos no \textit{broker} \ac{MQTT} local
   \item \textbf{Redirecionamento:} Os dados são redirecionados de forma assíncrona do \textit{broker} \ac{MQTT} local para o \textit{broker} \ac{MQTT} remoto (utilizando o mecanismo de \textit{MQTT Bridging})
   \item \textbf{Transporte:} Os dados são transportados do \textit{broker} \ac{MQTT} local para um tópico Kafka via conector Kafka Connect
   \item \textbf{Armazenamento:} Os dados são consumidos do tópico Kafka e inseridos na base de dados através de um segundo conector Kafka Connect
\end{itemize}
