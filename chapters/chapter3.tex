\section{Requisitos Funcionais e Não Funcionais}\label{sec:requirements}

De modo a guiar a criação deste trabalho, foi estabelecido um conjunto de requisitos funcionais e não funcionais que a solução deve respeitar.

\subsection{Requisitos Funcionais}

\begin{enumerate}[label=\textbf{FR.\arabic*},ref=FR.\arabic*]
    \item~\label{fr:1} O sistema deve ser capaz de receber e agrupar dados de várias fontes associadas ao mesmo utilizador.
    \item~\label{fr:2} O sistema deve ser capaz de receber e processar dados de diferentes sensores associados a um mesmo utilizador em simultâneo.
    \item~\label{fr:3} O sistema deve permitir ao utilizador visualizar os dados recolhidos em tempo real e com uma janela temporal de pelo menos 1 minuto, de modo a permitir identicar falhas nos sensores.
    \item~\label{fr:4} O sistema deve permitir o controlo de todos os sensores associados ao utilizador de forma centralizada.
    \item~\label{fr:5} O sistema deve ser capaz de identificar os sensores disponíveis e monitorizar durante a sessão que sensores estão a enviar dados.
    \item~\label{fr:6} O sistema deve ser capaz de detetar falhas na recolha ou no envio de dados e permitir ao utilizador detetar o momento da falha.
    \item~\label{fr:7} O sistema deve ser capaz de gerar uma estimativa do nível de atenção do utilizador em tempo real utilizando os dados dos sensores disponíveis.
\end{enumerate}

\subsection{Requisitos Não Funcionais}

\begin{enumerate}[label=\textbf{NFR.\arabic*},ref=NFR.\arabic*]
    \item~\label{nfr:1} O sistema deve funcionar corretamente mesmo quando apenas um subconjunto dos sensores é utilizado.
    \item~\label{nfr:2} O sistema deve permitir que os recursos sejam ajustados com base na dimensão do estudo e no número de utilizadores e sensores.
    \item~\label{nfr:3} O sistema deve detetar falhas em sensores em até 1 segundo após a interrupção no envio de dados, de forma que o utilizador seja informado sobre a falha.
    \item~\label{nfr:4} O sistema deve permitir a adição de mais sensores sem modificar a estrutura pré-existente.
    \item~\label{nfr:5} Os plugins de cada sensor devem recolher e enviar dados de forma autónoma, sem depender do funcionamento de outros plugins.
    \item~\label{nfr:6} O modelo preditivo deve gerar uma previsão (mesmo que menos precisa) mesmo que os dados de um ou mais sensores estejam em falta.
\end{enumerate}

\section{Arquitetura do Sistema}
\label{sec:arquitecture}

O sistema presente na Figura~\ref{fig:sys_arq} possui uma arquitetura descentralizada à base de eventos, que pode ser divido em 2 secções: \textbf{componentes locais} (que são executados no computador ou wearable do próprio utilizador) e \textbf{componentes externos} que serão executados de forma remota num servidor ou na cloud.

\begin{itemize}
    \item \textbf{Componentes locais:}
    \begin{itemize}
        \item \textbf{App para \textit{Desktop}:} Esta app feita em Python será o principal ponto de acesso por parte do utilizador e permitirá ao utilizador não só controlar todos os sensores de forma centralizada (iniciar ou parar uma sessão e definir que sensores serão utilizados em cada sessão), mas também ver os valores medidos pelos sensores e a evolução do seu nível de atenção ao longo de cada sessão.
        \item \textbf{\textit{Plugins} para sensores locais:} Cada sensor presente no computador do utilizador (teclado e câmara) terá o seu próprio \textit{plugin} responsável por recolher os dados do respetivo sensor, remover informação irrelevante e enviar as medições para o Kafka. Estes \textit{plugins} serão controlados diretamente pelo utilizador através da app.
        \item \textbf{\textit{Broker} MQTT local:} Este broker irá correr localmente no computador do próprio utilizador e servirá não só como meio de comunicação entre os sensores e o programa principal, mas também servirá como \textit{buffer} dos dados, permitindo o envio eventual dos dados, mesmo que o \ac{MQTT} remoto esteja em baixo.
        \item \textbf{App para \textit{WearOS}:} Esta app em Kotlin permitirá a medição de \ac{HRV} (extrapolado através dos batimentos por minuto) e o envio destes para o \textit{broker} \ac{MQTT} local.
    \end{itemize}
    \item \textbf{Componentes externos:}
    \begin{itemize}
        \item \textbf{\textit{Broker} MQTT remoto:} Serve como intermediário entre o cliente e o Kafka. A adição deste componente melhora a escalabilidade e a segurança do sistema ao evitar que cada cliente necessite de estabelecer conectores entre o broker local e o Kafka.
        \item \textbf{Kafka Connect:} O Kafka Connect estabelece conectores entre o broker \ac{MQTT} remoto e o Kafka, bem como a exportação destes dados para  a base de dados, permitindo uma ingestão automática e agnóstica ao tipo de sensor.
        \item \textbf{Kafka:} O Kafka permite gerir o fluxo de dados entre os plugins e os respetivos consumidores, garantindo a entrega de mensagens de forma escalável e com uma persistência de dados melhor que o padrão \ac{MQTT}, levando a uma melhor tolerância a falhas ou atrasos.
        \item \textbf{InfluxDB:} Base de dados \textit{Time Series} onde os dados são armazenados após serem processados e alimenta a app para \textit{desktop}. InfluxDB em particular foi escolhido visto ser a base de dados Time Series com a melhor documentação e suporte que encontrei até agora.
        \item \textbf{API REST:} API FastAPI que regula o acesso à base de dados e evita injeção de \textit{queries}. Utiliza parâmetros para a construção da \textit{query}, permitindo versatilidade sem por em risco a segurança do sistema.
    \end{itemize}
\end{itemize}
